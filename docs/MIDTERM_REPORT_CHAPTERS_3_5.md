# 3 研究目标及研究内容

## 3.1 总体研究目标

本课题面向 Ascend NPU 大模型训练过程中检查点数据规模大、保存路径长、后台 I/O 控制复杂以及频繁全量写入开销高等问题，研究基于 NPU 与本地 NVMe 协同的高频检查点系统。课题的总体目标是在保证检查点状态一致、数据完整、持久化结果可识别且能够正确恢复的前提下，缩短模型状态从 NPU 高带宽内存到 NVMe 设备的持久化路径，降低检查点操作对训练主流程的阻塞，并探索利用 NPU 侧计算资源在数据离开设备内存之前完成增量筛选与压缩，从而形成一条覆盖“检查点生成—异步调度—持久化写入—故障恢复”的端到端技术链。

围绕上述总体目标，本课题将检查点开销分解为数据量、数据路径和控制调度三个相互关联的层次。首先，针对传统框架检查点需要经过对象序列化、文件系统和通用内核 I/O 栈的问题，构建由 Ascend ACL 与 SPDK 组成的文件系统旁路数据通路，实现 NPU HBM、SPDK DMA 缓冲区与裸 NVMe 设备之间的大块分段传输。其次，针对 Python 训练线程、NPU 运行时和 SPDK 异步 I/O 之间的并发协调问题，构建由单一 CPU 线程执行的 Reactor 控制平面，使 SPDK queue pair 始终由固定线程拥有，并通过请求环、有限状态机和轮询器推进检查点操作。最后，针对全量检查点写入量与模型状态规模成正比的问题，研究 NPU 图内块级差分、Top-K 选择与 INT8 量化方法，通过周期性全量检查点与增量检查点相结合，减少高频保存时实际写入 NVMe 的数据量。

课题预期形成的系统并非简单叠加三项彼此独立的优化，而是以统一的检查点语义将其连接起来：NPU 图内增量计算决定“需要写入哪些数据”，Reactor 控制平面决定“何时以及如何安全地调度写入”，SPDK 数据通路负责“以较低软件开销完成数据持久化”。三者分别对应检查点的数据生成层、控制层和执行层，共同服务于降低训练停顿、提高持久化带宽和控制恢复误差的总体目标。

## 3.2 具体研究目标

### 3.2.1 构建基于 SPDK 的检查点读写数据通路

第一项研究目标是面向 Ascend NPU 构建文件系统旁路的全量检查点读写通路。系统应能够获得模型参数在 NPU HBM 中的地址及长度，将连续或离散的参数区域转换为满足 4 KiB 对齐约束的批量 I/O 任务，并使用固定大小的 SPDK DMA 缓冲区池完成分块搬运。写入过程中，数据依次经过“HBM 到 DMA 缓冲区”和“DMA 缓冲区到 NVMe”两个阶段；读取过程执行相反方向的数据传输。通过在多个缓冲区之间交叠 ACL 数据搬运和 SPDK NVMe 命令，降低串行执行两个阶段造成的等待。

除数据搬运外，该目标还包括面向裸盘的检查点数据组织。系统需要在不依赖文件目录和文件元数据的情况下，明确描述设备格式、当前有效元数据版本、各训练 rank 的检查点槽位以及每个参数的名称、形状、数据类型、设备偏移和长度。为此，项目设计超级块、双元数据槽和循环复用的全量检查点区域，并由 Python 层的 `DirectCheckpoint` 负责格式化、挂载、保存、加载和检查。该目标最终应实现可重复的全量保存与恢复，获得接近本地 NVMe 顺序写能力的端到端吞吐，并对对齐、越界、版本切换和数据一致性进行验证。

需要强调的是，本课题当前实现利用 ACL 在 NPU HBM 与主机侧 DMA 缓冲区之间搬运数据，再由 SPDK 访问 NVMe，属于文件系统旁路的用户态分块流水线，而不是 NPU 与 NVMe 之间的硬件 PCIe P2P，也不宣称实现了严格意义上的完全零拷贝。研究重点是减少通用软件路径、组织有界流水线并形成完整检查点语义。

### 3.2.2 构建基于 CPU 单线程的 Reactor 控制平面

第二项研究目标是建立符合 SPDK queue pair 单所有者约束的异步检查点控制平面。系统由固定 Reactor 线程统一创建、使用并回收数据和元数据 I/O 资源，Python 训练线程及其他控制线程不直接操作 SPDK queue pair，而是将写、读或元数据请求提交到无锁请求环。Reactor 在轮询循环中取出请求，通过写有限状态机、读有限状态机和元数据轮询器逐步推进操作，并在完成后更新请求状态或通知上层。这样可以把检查点生命周期中持续时间较长的 I/O 操作从训练线程移出，同时避免多个线程通过大粒度互斥锁竞争同一 qpair。

该目标还包括面向训练步的 Fire-and-Forget 触发机制。训练图在 NPU HBM 中维护步数计数器，Reactor 以较低频率读取计数器；达到设定的检查点间隔后，控制平面启动预先注册的数据写入任务，并保证同一时刻至多存在一个后台持久化任务。持久化完成后，Reactor 将完成值写回 NPU 侧 `probe_flag`，使训练程序能够在不同步等待整个 I/O 过程的情况下观测检查点进度。该目标的重点不是单纯使用“一个线程”，而是形成“资源单所有者、跨线程消息传递、状态机分步推进和设备侧完成通知”的统一控制机制。

### 3.2.3 探索基于 NPU 的增量检查点压缩方案

第三项研究目标是研究在 NPU 训练图内生成块级增量检查点的方法。系统维护当前参数状态与上一检查点状态，将大参数展平并划分为固定大小的数据块，在图内计算参数差值及块级变化范数，选择变化较显著的 Top-K 数据块，再对选中差值执行 INT8 量化，输出量化数据、缩放因子、块索引和版本信息。相对于先把完整参数传回 CPU 再比较和压缩，该方案希望利用 NPU 侧 Vector 计算能力，在数据离开 HBM 之前完成筛选与编码，从源头减少后续 ACL 搬运和 NVMe 写入量。

增量检查点不能脱离恢复过程单独评价。因此，本课题同时研究周期性 FULL 与 Delta 链结合的恢复协议：以最近一次全量检查点作为基线，在其后依次保存若干 Delta；发生故障后，首先读取 FULL，再按照版本顺序反量化并应用 Delta。研究将重点考察块大小、Top-K 比例、量化位宽、FULL 间隔与恢复误差之间的关系，并针对固定 Top-K 可能长期遗漏小幅变化、量化误差随链长累积等问题，探索自适应选择、周期性刷新或误差反馈机制。中期阶段以方案设计和关键可行性验证为目标，完整的多步保存—恢复闭环及性能优化属于下一阶段工作。

## 3.3 主要研究内容

### 3.3.1 面向裸 NVMe 的检查点数据组织与批量 I/O

项目首先研究模型状态如何从训练框架中的参数集合转换为裸盘上的连续或分段数据。Python 层遍历模型参数，记录参数名、形状、数据类型、内存地址和字节数，并根据默认 4 MiB 分块大小将其转换为批量任务。C 层提供 NPU 和 Host 两类批量读写接口，分别处理设备地址与主机地址来源的数据。对于不满足整块长度的尾部数据，系统在保证 4 KiB 对齐的条件下计算有效长度和磁盘占用，避免裸 NVMe 命令因地址或长度不符合要求而失败。

裸盘布局方面，当前原型在设备起始位置依次设置 4 KiB 超级块、两个各 400 KiB 的元数据槽和数据堆区域。超级块记录格式标识与当前有效元数据槽，元数据槽保存检查点版本、rank、step、参数布局及数据区域位置；全量数据按照 rank 和 `step % keep_last_n` 映射到循环槽位。保存时先写入数据，再将新元数据写入非活动槽，最后切换超级块中的活动槽标记，以降低元数据更新中断导致旧版本和新版本同时失效的风险。读取时先解析超级块与活动元数据，再据此重建参数分块和批量读任务。

### 3.3.2 ACL 与 SPDK 协同的有界分块流水线

数据面以固定数量的 DMA 缓冲区构成有界缓冲池，避免为整个模型额外分配一份等大的主机快照。写入状态机取得空闲缓冲区后，启动从 NPU HBM 到 DMA 缓冲区的 ACL 异步拷贝；拷贝完成后，在同一个 Reactor 线程中向 SPDK qpair 提交 NVMe 写命令；SPDK completion 返回后释放缓冲区供后续块复用。读取状态机则先将 NVMe 数据读入 DMA 缓冲区，再启动到目标 HBM 地址的 ACL 拷贝。通过调节分块大小和 pipeline depth，可以在缓冲区占用、命令并发度、ACL 搬运效率和 NVMe 顺序带宽之间取得平衡。

本部分还研究 NPU 运行时上下文与 SPDK 线程模型的协同问题。Reactor 线程需要绑定正确的 ACL context，同时负责 SPDK 轮询、DMA 事件查询和 completion 回收；初始化与清理阶段需要按照资源依赖顺序创建和销毁线程、qpair、DMA 缓冲区、请求环及 ACL 对象。中期之后将继续完善异常传播、超时和失败回滚，保证部分初始化失败或单个 I/O 命令失败时，上层能够获得明确错误而不是无限等待。

### 3.3.3 单所有者请求环与有限状态机

控制平面研究内容包括写请求环、读请求环和元数据请求环的组织方式，以及跨线程生产者—消费者同步。Python 侧通过 ctypes 调用 C ABI，C 接口仅负责校验和构造任务、将请求放入环中并等待或返回；真正的 qpair 操作始终发生在 Reactor。考虑到实验平台为 ARM64，环中请求状态发布与读取需要使用 acquire/release 内存语义，确保任务描述在消费者可见时已经完整写入。

一次大模型检查点会包含大量数据块，若在轮询器单次调用中同步完成全部搬运和 I/O，会长时间占据 Reactor，使元数据请求、读取请求和训练步检查失去响应。因此，项目使用有限状态机将一次批量操作拆分为“收集完成—提交已就绪缓冲区—启动一个新 DMA 阶段—检查 DMA 完成”等短步骤，每次轮询仅执行有界工作。读、写状态机可以独立推进，元数据使用独立 qpair，训练步轮询器则以约 10 ms 的周期检查 NPU 计数器。该设计使不同控制任务在单线程中协作执行，同时保持 SPDK 资源所有权清晰。

### 3.3.4 训练步触发与持久化完成通知

项目在 C 层提供任务预注册接口，用于提前登记待写入的数据地址、长度和磁盘偏移，减少检查点触发时的临时构造开销。训练图每完成一步更新 NPU 侧 step counter，Reactor 定期将其读取到主机；当计数器达到新的触发点且当前没有飞行中任务时，控制平面将预注册任务交给写状态机。完成后，Reactor 把约定的状态值写到 `probe_flag` 对应设备地址。训练侧只需推进计数器和按需读取标志，无需在每次触发时进入同步保存函数，从而形成 Fire-and-Forget 路径。

该机制仍需与检查点版本、元数据提交和错误状态结合。后续将把“数据写入完成”“元数据提交完成”和“检查点可恢复”区分为明确状态，避免仅凭数据 DMA 完成即报告整个检查点成功；同时补充超时、取消和清理期间的在途请求处理。

### 3.3.5 NPU 图内块级 Delta、Top-K 与 INT8 量化

项目在 `DeltaTrainCell` 中将训练与增量检查点计算组织为连续阶段：执行训练更新；聚合当前参数并重建上一版本近似值；计算块级 Delta 范数；选择 Top-K 块；对选中块进行 INT8 量化；更新用于下一次比较的旧参数状态；最终输出量化数据、scale、index 和步数。当前默认大参数块包含 524288 个元素，对 FP16 参数约对应 1 MiB 原始数据，Top-K 比例默认设为 10%。较小参数需要使用独立路径处理，以免固定分块带来过高填充或索引开销。

中期研究不仅验证算子是否能够在 GRAPH_MODE 中编译和输出有效设备缓冲区，还比较图内输出与参考计算的块选择重合度、量化差异和恢复 NRMSE。现有验证发现 INT8 量化本身误差较小，但固定 Top-K 在长恢复链中会遗漏多次小幅变化的块，导致误差显著累积。这一负面结果构成后续方案改进的重要依据：增量选择策略不能只追求单次压缩率，还需要对累计未保存变化进行补偿，并通过周期性 FULL 限制恢复链长度。

## 3.4 拟解决的关键问题

本课题拟重点解决以下四类问题。

第一，解决 NPU 运行时与用户态 NVMe 驱动之间缺少直接检查点语义的问题。ACL 负责设备内存搬运，SPDK 负责 NVMe 命令，两者只提供底层能力；项目需要在其上建立参数分块、对齐映射、缓冲区复用、元数据提交和版本恢复机制，才能把一次批量数据传输转化为可识别、可恢复的检查点。

第二，解决异步检查点与 SPDK 单线程资源所有权之间的矛盾。训练线程希望快速提交并返回，而 qpair 不能被多个线程无序操作。项目通过单所有者 Reactor、请求环和有限状态机把“跨线程提交”与“单线程执行”分离，并使元数据、读、写和步数触发共享同一事件驱动框架。

第三，解决裸盘高性能访问与可靠版本管理之间的矛盾。绕过文件系统后，系统失去了目录、文件长度、原子重命名等通用机制，必须自行维护磁盘区域边界、活动版本、参数布局和恢复顺序。项目通过超级块、双元数据槽、循环 FULL 槽以及规划中的 Delta ring 和帧头构建自描述格式，并将在下一阶段统一 FULL 与 Delta 的空间分配，避免区域重叠。

第四，解决增量检查点压缩率、计算开销和恢复精度之间的权衡。Top-K 比例较低能够减少写入量，却可能遗漏持续的小变化；比例较高则会削弱压缩收益。INT8 量化进一步缩小数据，但需要正确保存每块 scale，并控制多步反量化误差。课题将以端到端恢复 NRMSE、训练精度、写入数据量、图内计算开销和恢复时间为共同指标，而不是只评价单次压缩率。

## 3.5 技术路线调整及任务边界

开题阶段以 GPU/BaM 直通存储和多路径写入作为预期技术路线。进入实现阶段后，课题根据可获得的 Ascend 910B、MindSpore、CANN/ACL 和 SPDK 实验环境，将具体实现对象调整为 NPU 检查点系统。调整前后所研究的核心问题保持一致，仍然是如何缩短加速器训练检查点数据路径、如何安全地将持久化与训练重叠以及如何降低写入数据量；变化主要体现在底层接口由 GPU 生态接口调整为 ACL+SPDK，并在工程实践中进一步形成单所有者 Reactor 和 NPU 图内压缩两项研究内容。

| 开题阶段预期方向 | 当前项目实现 | 延续的研究问题 |
|---|---|---|
| GPU/BaM 访问 SSD | Ascend ACL + SPDK 分块流水线 | 缩短加速器检查点持久化路径 |
| GPU 侧或多线程轮询优化 | CPU 单所有者 Reactor + 请求环 + FSM | 降低同步等待、锁竞争和资源越权访问 |
| 多路径写入与 SSD 缓冲优化 | 裸盘 FULL 槽、双元数据槽与规划中的 Delta ring | 提升持久化效率并保证版本可恢复 |
| 开题阶段未充分展开 | NPU 图内 Delta + Top-K + INT8 | 从源头减少高频检查点写入量 |

本课题当前的系统边界为单机 Ascend NPU 与本地 NVMe 的检查点原型。多 rank 数据布局已预留 rank 维度，但跨节点一致性、共享存储容灾、弹性重分片和大规模集群调度不作为中期阶段的完成条件。检查点状态以模型参数为主要验证对象，优化器、随机数状态和数据加载位置将在端到端训练恢复实验中逐步补齐。

# 4 研究方案与技术路线

## 4.1 总体研究方案

本课题采用“先打通全量数据通路，再重构异步控制平面，最后引入图内增量压缩”的递进式研究方案。第一阶段以正确完成 NPU/Host 数据与裸 NVMe 之间的批量写入和读取为目标，验证 ACL、SPDK、DMA 缓冲区及裸盘布局的可行性；第二阶段将原有同步或多线程 I/O 迁移到固定 Reactor 线程，通过请求环和有限状态机形成统一控制平面，并增加训练步触发的 Fire-and-Forget 路径；第三阶段在前两阶段提供的持久化能力之上，研究 NPU 图内生成压缩 Delta，并建立周期性 FULL 与 Delta 链的恢复协议。

从软件层次看，系统由训练与图内计算层、Python 检查点管理层、C 控制与数据层以及裸 NVMe 存储层构成。训练与图内计算层基于 MindSpore，负责模型更新、步数计数和增量数据生成；Python 层的 `DirectCheckpoint`、`DeltaTrainCell` 等模块负责参数发现、任务编排、磁盘布局和元数据；C 层的 `libnpu_nvme.so` 提供稳定 ABI，内部包括请求环、Reactor、读写 FSM、ACL 搬运、SPDK qpair 和缓冲池；存储层保存超级块、双元数据槽、全量检查点槽和增量帧。Python 层与 C 层之间只传递地址、长度、偏移和状态，不在接口处重新序列化大块张量数据。

## 4.2 基于 SPDK 的检查点数据通路

### 4.2.1 裸盘布局与元数据提交

项目使用自定义裸盘格式绕过通用文件系统。当前布局起始部分为 4 KiB 超级块，随后是两个各 400 KiB 的元数据槽 A 和 B，数据堆从 804 KiB 偏移开始。超级块包含固定魔数 `NPUNVME1`、格式版本和活动元数据槽等信息；元数据采用 JSON 描述检查点 step、rank、参数名称、shape、dtype、数据偏移及长度。两个元数据槽交替使用，使新检查点元数据能够先完整写入非活动槽，再通过更新超级块切换活动版本。

全量检查点数据按 rank 分组，并按 `step % keep_last_n` 选择循环槽位。保存流程采用“数据先行、元数据后提交”的顺序：首先完成全部参数数据写入；其次生成指向新数据的元数据并写入非活动槽；最后切换超级块活动槽。读取流程先校验超级块魔数和格式版本，再读取活动元数据，据此构造参数的磁盘偏移与目标内存地址。该方法不能等同于通用文件系统事务，但能使保存过程中断时保留上一活动元数据作为恢复入口。

现阶段 FULL 区域主要由 Python 层根据设备容量和保留版本数规划，Delta ring 则由 C 层布局逻辑管理。下一阶段需要引入统一空间分配器或在超级块中固化各区域边界，保证 FULL 槽与 Delta ring 不发生物理重叠，并为格式升级、坏版本隔离和磁盘空间检查提供基础。

### 4.2.2 全量检查点分块写入

全量保存由 Python 层收集参数地址和长度，并将其转换为若干对齐任务。当前默认 chunk size 为 4 MiB，大参数被拆分为多个 chunk，小于一个 chunk 的尾部按实际有效字节搬运并按 NVMe 访问要求分配磁盘空间。任务提交到 C 层后，写状态机从空闲缓冲区 ring 中取得 DMA 缓冲区，使用 ACL 启动 HBM 到 DMA buffer 的异步拷贝；事件完成后，由 Reactor 使用所属 qpair 提交 SPDK 写命令；NVMe completion 到达后，该缓冲区重新进入空闲 ring。

当 pipeline depth 大于 1 时，不同 chunk 可处在不同阶段：一个缓冲区正在进行 HBM 拷贝，另一个缓冲区已经向 NVMe 提交，之前的命令可能正在等待 completion。状态机每次轮询只启动或回收有限数量的工作，既保持流水线连续，又避免单个请求长期独占 Reactor。对于 Host 源数据，系统提供对应批量写接口，跳过设备到主机搬运或使用适当的主机复制路径，以便独立验证 SPDK 数据面。

### 4.2.3 检查点读取与恢复

全量加载时，`DirectCheckpoint` 读取活动元数据并将每个参数映射到一组读任务。读状态机先向 NVMe 提交读取，将数据放入 SPDK DMA 缓冲区；命令完成后，再使用 ACL 把有效数据复制到目标 HBM 地址。所有任务完成后，上层可通过参数校验、逐字节比较或恢复后模型输出比较确认数据一致性。Host 目标也保留了独立接口，用于不依赖 NPU 计算的存储回读测试。

读取路径与写入路径在结构上镜像，但二者的完成语义不同：写入完成后还需要提交元数据，读取完成后则必须保证最后一次 DMA 回填已经结束，参数才可被训练图使用。当前项目已打通加载 API 和阶段性回读流程，但正式中期数据中尚缺少当前版本的统一读取带宽与恢复时间，因此本报告只将读取作为功能性成果，不据此声称读性能已经达到特定数值。下一阶段将重点回归 Host/NPU 目标类型、尾块处理、错误传播和加载后模型一致性。

### 4.2.4 元数据一致性与异常处理

为避免数据尚未持久化就暴露新版本，系统将元数据提交置于数据任务完成之后。元数据请求通过独立请求环和独立 meta qpair 在 Reactor 内执行，避免与大块数据读写共享不清晰的锁生命周期。对于保存中途失败的情况，上层应保持旧活动槽不变，并将新数据区域视为不可恢复的未提交版本。对于读取失败，状态机应中止后续回填并将错误码返回 Python。

目前正常路径已形成，但健壮性仍需完善，包括 SPDK completion 错误向上层传递、请求等待超时、初始化失败回滚、cleanup 期间在途任务处理以及 meta qpair 的单一资源所有权。后续将通过故障注入和重复初始化—清理测试验证这些异常路径。

## 4.3 基于 CPU 单线程的 Reactor 控制平面

### 4.3.1 设计动机与演进过程

早期实现由调用线程直接进入数据路径，或者使用额外监听线程和全局 `io_lock` 协调检查点操作。这种方式虽然容易建立原型，但会使 qpair 的实际访问线程随调用路径变化，大粒度锁还可能覆盖整个批量 I/O 生命周期，使读、写、元数据或清理路径相互阻塞。针对这些问题，项目逐步建立固定 Reactor 线程，并将所有 SPDK I/O 操作迁移到该线程。

控制平面经历了从 V0 到 V6 的演进：V0 验证 SPDK thread/poller 框架；V1 将 Reactor 线程纳入库的初始化与清理；V2 用 step poller 替代独立监听线程；V3 引入写请求环和异步写 FSM；V4 增加异步读 FSM与独立元数据 qpair，并移除覆盖 I/O 生命周期的 `io_lock`；V5 清理旧同步路径；V6 修复状态机与清理回归并增加 C 层批量计时。演进过程表明，单线程控制平面并非一次性封装，而是围绕资源所有权、异步进度和可观测性逐步形成。

| 版本 | 主要工作 | 解决的问题 |
|---|---|---|
| V0 | 建立 SPDK thread/poller 骨架 | 验证 Reactor 可运行性 |
| V1 | Reactor 纳入初始化与清理 | 固定 I/O 执行线程生命周期 |
| V2 | step poller 替代 listener thread | 统一训练步触发入口 |
| V3 | write ring + async write FSM | 写入迁移为消息提交和分步执行 |
| V4 | async read FSM + meta qpair，移除 `io_lock` | 统一读取并解耦元数据与大块 I/O |
| V5 | 删除旧同步路径、整理调试输出 | 消除重复实现与所有权歧义 |
| V6 | 修复状态机和清理回归，增加 C 层计时 | 建立当前阶段性能基线 |

### 4.3.2 请求提交与线程所有权

控制平面的基本执行过程如下：Python 通过 C ABI 提交一组任务；C 接口分配请求上下文，复制必要的任务描述并将其放入 write、read 或 meta ring；Reactor 轮询对应 ring，取出请求后将其挂接到相应 FSM；FSM 只在 Reactor 线程中调用 ACL 事件查询、SPDK qpair 操作和 completion 处理；任务完成后更新原子状态或完成标志；同步 API 可以等待该状态，Fire-and-Forget API 则立即返回并通过设备标志异步通知。

这种结构将共享状态限制在请求描述、环首尾位置和少量监听配置上，`state_lock` 只保护控制配置，不覆盖 I/O 生命周期。ARM64 上使用 acquire/release 屏障保证生产者先写完整请求再发布，消费者在看到请求后能够读取一致内容。通过将资源所有权设计为结构性约束，而不是依赖调用者遵守约定，可以降低后续增加 Python 线程或后台任务时引入 qpair 并发访问的风险。

### 4.3.3 写、读和元数据状态机

写 FSM 每轮首先收集 SPDK completion 并释放已经完成的槽位，其次为 ACL 搬运已完成的缓冲区提交 NVMe 写命令，再尝试为新 chunk 获取空闲缓冲区并启动一次 HBM 到 DMA 的拷贝，最后记录正在等待的 ACL event。读 FSM执行镜像过程：收集 NVMe 读取完成，启动 DMA 到 HBM 的回填，回收回填完成的缓冲区，再向空闲缓冲区提交新的 NVMe 读请求。元数据请求规模较小，由独立 poller 和 qpair 执行，以免被长批量任务阻塞。

有限状态机的价值在于将单次轮询工作限制在可控范围，使 write、read、meta 和 step poller 能在同一线程中共同取得进展。后续实验将进一步记录每轮处理上限、队列深度和长尾延迟，确认在大检查点压力下元数据和训练步触发仍具有可接受响应时间。

### 4.3.4 训练步级 Fire-and-Forget

Fire-and-Forget 路径将检查点触发从 Python 同步函数调用改为设备步数驱动。初始化阶段由上层设置 step counter 和 probe flag 的设备地址，并注册待写入任务。训练图完成参数更新后递增 step counter；step poller 约每 10 ms 读取一次该值，判断是否越过新的保存间隔。当条件满足且不存在飞行中写入时，Reactor 启动任务；若上一检查点仍未完成，则不并发启动第二个任务，避免多个版本竞争同一缓冲池或槽位。完成值经 ACL 写回 probe flag，训练程序可以低成本确认持久化进度。

该路径能够减少 Python 位于训练关键路径上的调用次数，但它本身不自动解决一致性问题。注册地址对应的数据必须在被读取期间保持逻辑稳定，或者系统需要建立显式快照/版本缓冲。下一阶段将结合 FULL 槽切换与 Delta 输出缓冲生命周期，明确触发时刻、数据冻结窗口、元数据提交完成点和可恢复版本之间的关系。

## 4.4 基于 NPU 图内计算的增量检查点方案

### 4.4.1 参数分块与旧版本表示

增量方案将模型参数按照稳定顺序展平，并把大参数切分为固定元素数的块。每个块具有全局 block index，同时可以映射回参数编号和参数内偏移。系统保留上一检查点状态 `P_old`，在当前训练步得到 `P_current` 后计算 `Delta = P_current - P_old`。为降低 `P_old` 的 HBM 占用，原型尝试使用 INT8 表示旧状态；但正确反量化需要为每块维护对应 scale，当前实现仍需补齐完整 scale 生命周期和小参数路径。

块大小决定范数计算粒度、索引数量和压缩选择自由度。块过大时，一个局部变化会导致整个大块被保存；块过小时，范数、Top-K、索引和 scale 数量上升，图编译与运行开销也会增加。后续将以 524288 元素的当前默认值为中心扫描多种块大小，并分别记录压缩率、图内耗时和恢复误差。

### 4.4.2 图内变化检测、Top-K 与量化

对每个数据块，训练图计算 Delta 的范数作为变化度评分，再从全部候选块中选择 Top-K。选中块按照块内最大绝对值计算量化 scale，并将 FP16/BF16 差值映射为 INT8；输出缓冲包括量化块数据、scale、index、有效块数、step 和必要的版本信息。未选中块的变化不能简单丢弃，应在 `P_old` 或残差缓冲中累积，以便后续变化达到阈值时被选中。当前原型已经完成图内算子链和单步输出验证，但残差反馈与完整旧版本更新仍是下一阶段重点。

从数据量估算看，若从约 3000 个块中选择 10%，并把选中 FP16 Delta 量化为 INT8，则主体数据量约为全量 FP16 的 5%，另有 scale、index 和帧头等少量开销。这说明 Top-10% 与 INT8 组合具有较大的理论写入缩减空间，但最终收益必须扣除图内计算时间、旧状态维护、周期性 FULL 和恢复重放成本。

### 4.4.3 FULL + Delta 持久化与恢复协议

增量检查点以周期性 FULL 为恢复基线。每个 Delta 帧至少需要记录格式版本、基线 FULL 标识、训练 step、块大小、有效块数、量化类型、数据段长度及校验信息；帧内按确定顺序保存 block index、scale 和量化数据。写入时由 Reactor 将图内输出缓冲分块注册并写入 Delta ring，帧完成后再提交版本状态。恢复时选择最近的有效 FULL，加载到 NPU 后按 step 顺序读取 Delta，对选中块执行反量化和加法更新，直到目标版本。

为了限制恢复链过长和误差累积，系统需要设置最大 Delta 数或最大累计误差阈值，达到条件后强制生成新的 FULL。若某次 Delta 损坏，应能回退到上一有效版本而不是继续应用后续帧。当前 C 层已有 Delta layout 查询和 ring 相关接口，Python 侧也已有帧协议草案，但 FaF 原始缓冲格式、磁盘帧头与自描述恢复格式尚未完全统一；这将作为下一阶段端到端闭环的关键任务。

## 4.5 正确性、性能与恢复验证方案

## 5.4 Reactor 控制平面阶段成果

### 5.4.1 单所有者异步路径已经形成

经过 V0—V6 的迭代，项目已经将批量写、批量读和元数据 I/O 统一迁移到 Reactor 线程，Python 调用线程通过请求环提交任务，不再直接持有 qpair。写和读状态机按 chunk 推进 ACL 与 SPDK 阶段，元数据使用独立 qpair，训练步检查由 step poller 完成。覆盖整个 I/O 生命周期的 `io_lock` 已移除，只保留保护少量控制状态的锁，从结构上减少了多线程竞争和 qpair 所有权不明确的问题。

阶段性测试中，V6 的顺序写性能没有因采用单 Reactor 而下降，1 GB 批量写的 Python/C 差异也仅约 0.5%。这说明在当前以大块顺序 I/O 为主的检查点负载中，一个 CPU 控制线程能够为数据面提供足够的命令提交和 completion 处理能力。该结论不等于单线程在所有并发度下都没有瓶颈，后续仍需测试同时存在读、写、元数据和训练步轮询时的公平性与长尾。

### 5.4.2 Fire-and-Forget 路径已经打通

项目已实现 step counter 设备地址设置、预注册任务、step poller 触发和 probe flag 完成通知。训练图更新计数器后，无需每到检查点步数就在 Python 中同步调用完整保存；Reactor 检测触发点后执行后台任务，并在持久化完成后把标志写回 NPU。历史 100 步阶段实验记录中，纯训练约为 412 ms/step，开启完整 FaF 路径后约为 435 ms/step，初步开销约 5.6%，最终完成标志达到预期值 10。

### 5.5.3 数据缩减与写入结果

阶段 Delta 输出数据量约为 159.4 MB，相对于约 3.12 GB 的 FP16 FULL 约占 5.1%，对应约 19.5 倍的数据量缩减。该比例与“Top-10% 块选择 + FP16 差值量化为 INT8”的理论估算基本一致，但尚未完整计入未来帧头、块索引、每块 scale、小参数和周期性 FULL 的平均开销。因此，19.5 倍应表述为本次 Delta 主体数据相对 FULL 参数数据的阶段比例，而不是整个长期检查点系统已经达到的最终压缩倍数。

现有写入实验将约 159.4 MB Delta 数据在约 45 ms 内写入，阶段有效带宽约为 3.35 GB/s，说明压缩输出能够沿现有持久化通路写出。与 FULL 相比，Delta 的绝对写入时间显著降低；但当前 FaF 注册和帧协议仍需支持大缓冲按 chunk 分解，ring slot 推进与元数据提交也需要统一，才能形成多版本持续写入。

### 5.5.4 单步恢复误差与长期误差发现

项目已完成一次单步恢复误差验证。该实验在 PYNATIVE 模式下从 2969 个块中选择约 296 个块，恢复 NRMSE 中位数为 0.002790，均值为 0.002144，最大值为 0.003065，95 分位数为 0.003004。结果表明，在单步条件下，选中块的 INT8 差分能够以较小相对误差恢复，为后续端到端协议提供了可行性依据。

但是，早期 100 步固定 Top-10% 实验的最终 NRMSE 中位数约为 0.76，明显高于单步结果。分析表明，固定比例只保存每一步变化最大的块，持续发生小幅变化但未进入 Top-K 的块会长期丢失；量化误差和旧版本近似也会随 Delta 链增长累积。因此，这组长期结果不是“恢复成功”的证明，而是说明固定 Top-K 方案存在根本限制，并直接推动后续引入残差反馈、自适应阈值和周期性 FULL。

### 5.5.5 图内计算开销的当前结论

现有原型的一次阶段测量出现约 189.3% 的附加开销，主要受图模式兼容问题、Host 侧临时 workaround 和尚未优化的旧状态更新路径影响。该数值说明当前原型还不具备直接部署价值，不适合包装为正面性能结果，也不能代表最终图内实现的合理上限。另一方面，历史输出中还出现过在 `P_old` 和量化输出实际为零时计算得到的 46.6% 开销，该测试没有执行有效 Delta 语义，因此本报告不采用该数据。

中期阶段对第三条主线的结论应限定为：图内 Delta/Top-K/INT8 已完成关键算子与输出缓冲可行性验证，数据缩减潜力和单步量化误差得到初步量化，但图内执行开销、长期恢复精度和自描述持久化协议尚未闭环。下一阶段将优先消除 Host workaround、补齐 per-block scale 与残差机制，再进行公平的端到端训练性能测量。

## 5.6 阶段性成果总结与当前问题

本课题中期阶段形成了以下可汇报成果：

1. 实现了面向 Ascend NPU 的 ACL+SPDK 文件系统旁路检查点数据通路，支持 NPU/Host 批量任务、4 KiB 对齐、默认 4 MiB 分块、有界 DMA 缓冲池和裸 NVMe 持久化。
2. 实现了超级块、双元数据槽和循环 FULL 槽，形成从参数布局、数据写入到版本提交和加载调用的基本检查点语义。
3. 完成单所有者 Reactor V0—V6 演进，建立 write/read/meta 请求环、异步读写 FSM、独立元数据 qpair、step poller 和 Fire-and-Forget 完成通知。
4. 在 GPT-2 XL 上获得平均约 804 ms 的 FP16 全量保存阶段结果，端到端有效带宽约 3.8 GB/s；V6 最佳顺序写带宽约 4.432 GB/s。
5. 完成 NPU 图内 Delta、Top-K 和 INT8 原型验证，阶段 Delta 主体数据约为 FULL 的 5.1%，单步恢复 NRMSE 中位数约为 0.00279。
6. 通过长期误差实验发现固定 Top-K 会造成显著误差累积，明确了残差反馈、自适应选择和周期性 FULL 的后续优化方向。

与此同时，项目仍存在若干必须在正式论文实验前解决的问题。数据通路需要完成 Host/NPU 读取回归、读取性能、错误传播和尾块/越界测试；控制平面需要修复初始化失败回滚、meta qpair 清理所有权、超时和在途任务回收；磁盘格式需要统一 FULL 与 Delta 区域分配；多 rank 元数据尚未形成完整提交语义。增量路径需要解决大缓冲按 chunk 注册、FaF ring slot 与帧头统一、`P_old` 每块 scale、小参数、块索引稳定映射、残差反馈和图内开销等问题。

这些问题不改变前两条主线已经打通的判断，但决定了系统能否从“可运行原型”进入“可复现、可比较、可恢复”的论文实验状态。下一阶段将遵循“正确性和资源安全优先—全量正式实验—Delta 端到端闭环—统一对比与论文整理”的顺序推进。

## 5.7 中期结论

综合项目实现、阶段实验和剩余任务，本课题已经完成总任务的约 70%，达到中期阶段完成三分之二左右任务的要求。基于 SPDK 的检查点数据通路和基于 CPU 单线程的 Reactor 控制平面已经形成可运行原型，并获得 GPT-2 XL 全量保存、批量接口开销和 Fire-and-Forget 路径的阶段结果；基于 NPU 的增量检查点压缩已经完成方案设计、图内算子链和单步恢复验证，同时识别出固定 Top-K 长期误差累积这一关键问题。

中期成果证明了“图内少写—后台稳控—用户态快传”总体路线的可行性，也明确了后续工作的重点不只是继续增加代码功能，而是统一 FULL 与 Delta 的检查点协议，补齐异常和恢复闭环，在同一软硬件版本上重新完成保存、加载、训练干扰、CPU 占用、压缩率和恢复精度实验。完成这些工作后，三个研究方向才能形成相互支撑的完整系统结论。
