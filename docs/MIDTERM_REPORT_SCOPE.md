中期报告建议采用以下总述：

> 本课题面向 NPU 大模型训练中的检查点开销问题，从数据传输、I/O 控制和数据缩减
> 三个层面开展研究。目前已完成基于 SPDK 的用户态 NPU–NVMe 检查点读写通路，
> 并完成面向 SPDK 队列单所有者约束的 Reactor 异步控制平面，实现了全量检查点
> 保存、加载、训练步触发的后台持久化和元数据管理。针对全量检查点数据量过大的
> 问题，已提出 NPU 图内块级增量检测与 INT8 量化方案，完成图编译、量化误差及
> 压缩数据写入的初步可行性验证，端到端多步恢复和性能优化仍在进行。

不建议写成“第三个创新点基本完成”。当前最稳妥的表达是：

- 前两个技术点已形成可运行原型，后续工作主要是健壮性修复和完整实验。
- 第三个技术点已完成理论动机、方案设计和单步/局部可行性验证。
- 整体进入“系统完善 + 第三方向收敛 + 正式实验”阶段。

## 3. 推荐的报告叙事结构

### 3.1 研究背景与问题定义

从三个瓶颈展开：

1. **传输路径长**：通用检查点需要框架序列化、文件系统和多级内存搬运。
2. **控制与训练耦合**：同步保存阻塞训练，多线程直接访问 SPDK qpair 又引入锁竞争。
3. **全量数据规模大**：GPT-2 XL 的 FP16 参数约 3.12 GB，频繁全量写入占用大量带宽。

对应提出“快传、稳控、少写”三层方案。

### 3.2 总体系统架构

建议给出一张总图，包含：

- MindSpore 模型与训练图；
- Python `DirectCheckpoint` 控制层；
- ctypes C ABI；
- write/read/meta 请求环；
- 单线程 reactor 和读写 FSM；
- ACL HBM↔DMA buffer；
- SPDK DMA buffer↔NVMe；
- step counter 与 probe flag；
- FULL 区、双元数据槽和规划中的 Delta ring。

本节只讲模块和数据流，不展开实现细节。

### 3.3 已完成工作一：SPDK 检查点数据通路

建议汇报以下内容：

1. 采用 SPDK 绕过通用文件系统路径，在用户态直接提交 NVMe 命令。
2. 通过 ACL 完成 HBM 与 SPDK DMA buffer 之间的数据搬运。
3. 使用 4 KiB 对齐、大张量分块和有界 DMA buffer 池。
4. 支持 NPU/Host 双向批量读写。
5. Python 层实现模型参数布局、循环槽、双元数据槽和全量保存/加载。
6. `format_npu_disk.py`、`inspect_npu_disk.py` 和 C smoke test 构成基本工具链。

注意：当前实现不是硬件 PCIe P2P，不应称为“完全零拷贝”。建议使用：

> 文件系统旁路的用户态分块流水化传输路径。

### 3.4 已完成工作二：Reactor 异步控制平面

建议按 V0–V6 的演进过程讲述：

| 版本 | 阶段成果 |
|---|---|
| V0 | 验证 SPDK thread/poller 的基本可行性 |
| V1 | 将 reactor pthread 接入初始化和清理流程 |
| V2 | 使用 step poller 替换独立监听线程 |
| V3 | 将写路径改造成请求环 + 异步写 FSM |
| V4 | 接入异步读 FSM 和独立元数据 qpair，移除 `io_lock` |
| V5 | 清理旧同步管线和诊断代码 |
| V6 | 修复清理回归并增加 C 层批次性能计时 |

本节的核心不是“只使用一个 CPU 线程”，而是：

- SPDK qpair 由单一 reactor 独占；
- Python 和训练线程只提交命令，不直接操作 qpair；
- 读、写和元数据请求通过环形队列卸载；
- FSM 将一次长 I/O 拆成有界的事件推进；
- step counter 在后台轮询，达到间隔时自动触发 FaF；
- 控制路径不再依赖覆盖整个 I/O 生命周期的递归互斥锁。

### 3.5 正在进行的工作：NPU 图内增量检查点

按“动机—方案—阶段结果—当前问题”组织，不写成完整成果。

#### 动机

已有 PMU 结果显示 GPT-2 XL 训练中 Vector ALU 利用率为 12.4%，估算空闲比例为
87.6%。因此提出利用 NPU Vector 计算资源在训练图内生成压缩检查点，减少传向 NVMe
的数据量。

#### 当前方案

1. 将大参数组织为固定大小的连续块。
2. 在 NPU 图内计算当前参数与上一版本的差值。
3. 计算每个块的变化范数并选择 Top-K。
4. 将选中块量化为 INT8，同时保存 scale 和块索引。
5. 将压缩缓冲注册到 FaF 路径，在训练步边界写入 NVMe。
6. 规划使用“周期性 FULL + Delta 链”进行恢复。

#### 已完成的阶段验证

- GPT-2 XL 图内原型可在 GRAPH_MODE 编译。
- 一次实验包含 3038 个块，Top-10% 选择 303 个块。
- NPU FP16 路径与 CPU FP32 参考的量化结果平均绝对差约 0.0002，最大差为一个
  INT8 量化 bin。
- 四个主要输出缓冲均获得有效 HBM 地址。
- 阶段实验将约 159.4 MB Delta 数据写入 NVMe，耗时约 45 ms，对应约
  3.35 GB/s。
- 单步离线恢复实验的参数 NRMSE 中位数约 0.00279，最大值约 0.00306。

#### 已识别的问题

- 早期 100 步实验中，固定 Top-10% 导致误差累积，最终 NRMSE 中位数约 0.76。
- 量化快照的 scale、小参数和块到参数的稳定映射尚未完全接入当前主线。
- FaF 原始缓冲格式与自描述 Delta frame 恢复协议尚未统一。
- Delta ring 与 FULL 槽需要统一分区。
- 图内计算开销仍然明显，现有不同版本的 overhead 数据不能直接横向比较。

在中期报告中，这些问题应被表述为“方案验证得到的关键发现”，并自然引出下一阶段
的自适应 Top-K、周期性 FULL、量化状态修正和端到端恢复工作。

## 5. 当前不能作为正式结论的数据

以下内容不应直接放入中期报告的“成果结论”：

1. `step1c_spdk_bw.json` 中约 56 GB/s 的 `pipeline_dma_mbs`。该数值高于单块
   PCIe Gen4 ×4 NVMe 的物理上限，计时口径明显不适合作为存储带宽。
2. 历史 `bench_full.json` 的 Delta overhead 46.6%。该次结果同时记录
   `p_old_nonzero=false` 和 `quant_nonzero=false`，已从开发分支移除，不能证明
   有效 Delta 工作负载。
3. 早期 189.3% 的单步 Delta overhead。该数据包含 CPU workaround 且样本过少，
   只能说明原型开销很高。
4. 100 步 NRMSE 曲线不能作为“恢复成功”证据。它反而说明固定 Top-10% 方案存在
   误差累积；而且当前 JSON 只保留单步结果，与 PNG 图的数据版本不一致。
5. 历史 `plot_figures.py` 依赖的 `baseline_results.json`、
   `operator_experiments_v2.json`、`vector_engine_profile.json`、
   `vector_quant_bench.json` 和 `spdk_results.json` 均不在工作区，无法重新生成图表。
6. CheckFreq、PCcheck 和 MindSpore save 的现行对比脚本已经重写，但没有保存当前
   版本的结果文件，因此暂时不能给出正式横向比较结论。
7. 未发现结构化的读取/加载带宽结果。中期只能说明读路径和数据回读曾通过 smoke
   test，不能声称读带宽与写带宽相同。

## 8. 答辩时的推荐表述

### 被问“是否真正完成三分之二”

> 课题包含数据通路、控制平面和增量压缩三条主线。前两条已经完成端到端原型并在
> Ascend 910B 与 PM9A3 NVMe 上运行验证，第三条已完成图内原型、量化和写入可行性
> 验证。按照模块完成度核算目前约为 70%，剩余工作集中在增量协议闭环、健壮性修复
> 和最终对比实验。

### 被问“前两个点是否还有问题”

> 当前原型已经可以完成检查点写入、读取和训练步触发的后台持久化。现阶段发现的
> 问题主要属于异常路径、资源回收和实验完备性，不影响核心架构已经打通的判断。
> 这些问题已形成明确清单，将在最终性能实验前完成修复和回归。

### 被问“第三个点为什么还算进展”

> 第三个方向不再停留在概念层面：已经完成 NPU PMU 动机分析、图内 Delta 和

> 100 步实验暴露出固定 Top-K 的误差累积问题，这正是下一阶段需要解决的核心研究
